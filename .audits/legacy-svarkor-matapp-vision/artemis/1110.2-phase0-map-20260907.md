## 1. Vision → vad som måste ändras (kontrakt mot POC)

POC (Kvällsmat) idag = butiksväljare + en deterministisk veckomeny. Framtidsvisionen lägger till:

| Vision-del | POC-status | Natur av ändring |
|---|---|---|
| Inloggning (auth) | saknas helt | NY komponent (auth) |

| Motor → 3 veckomenyförslag | motor ger 1 plan per seed | Ändring i planner (flera förslag) + API/frontend |
| Majoritet extrapris-ingredienser | greedy maximerar offert-träffar, garanterar INTE majoritet; offert-schema saknar referenspris (rabatt-storlek) | Ändring i offert-ingest (referenspris), normalisering (per-ingrediens extrapris-flagga), planner (ratio-tröskel) |
| Valda butikers reklamblad | POC fetcher/normalizer/scheduler finns (willys/ica/coop-feeds) | Återbruk; feed-funktion verifieras |

**Gränser / HAL-seams (integrationer, "HAL-klass"):**
- **Feed-adapter-seam** (den enda riktiga "HAL"-klassen): varje kedjas format mappas i
  `fetcher.grocer` + `normalizer.chain_mapper` (nu via CHAIN_MAP id-prefix/round). Nytt behov:
  referenspris/rabatt måste bäras genom RawOffer→NormalizedOffer→Offer. **Host-mock** för tester
  = injicerad httpx-lik `session` (redan i grocern: `pull_grocer(grocer_cfg, week_key, session=None)`).
  **Device** = verkliga kedje-API. Detta är den mbedtls/lwIP-klassens analytiska motsvarighet:
  *"vad måste resolva vid den faktiska feed-anslutningen"* besvaras av 164.1.
- **DB-seam**: alla tabeller på delade `database.Base` (motor). Ny tabell (users, profile) MÅSTE
  deklareras på samma Base före `init_db` (POC:s fix-2 idiom: importera modulen före boot).
- **Auth-seam**: server-sidig session (opak cookie) — ingen egen krypto, bibliotek (`argon2-cffi`).
- **Horisontell vault/validity-seam**: `app/config.py` sys.path-insert för motorn (R1) — ny kod måste
  laddas EFTER `_DEFAULT_MOTOR_REPO`-resolution så motorns `config`/`database` importeras rätt.

## 3. Beroenden — pilar en exekveringsordning kan läsas ur

```
auth → users-tabell (Base)                    [auth bygger på DB]
profile → users-tabell → Base                 [profil bygger på auth + DB]
offers-ingest → Base (offers-tabell)          [ingest bygger på DB]
offers-ingest → feeds (willys/ica/coop)       [extern dep]
motor/planner → recipes(Base) + offers(Base)  [optimerare bygger på DB]
  planner → (OBS: kräver referenspris i offers för "majoritet"-mätning)
api/menu → planner                            [API bygger på motor]
api/auth → auth ; api/profile → profile       [API ringer auth+profil]
frontend → api/*                              [frontend bygger på API]
```

**Exekveringsordning (topologisk):**
1. DB-grund (Base, users, profile, offers+referenspris, recipes) — inget annat utan den.
2. Auth (hashning + session) + Offer-ingest (referenspris-persistens). Dessa är oberoende av varandra → kan byggas parallellt.
3. Profil (lagring) — beror på auth + DB.
4. Optimering-motor (ratio-tröskel + 3 förslag) — beror på recipes + offers(+referenspris).
5. API-lager — beror på auth/profil/motor.
6. Frontend — beror på API.
7. Hosting/integration (hosting.yaml, PORT-bind, post-publish).
